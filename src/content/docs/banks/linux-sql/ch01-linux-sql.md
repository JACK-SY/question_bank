### Q1.（简答 ★）Linux 和 Windows 怎么杀死进程？请对相应命令给出说明。

> **参考答案**：
> - **Linux**：
>   - `ps -ef | grep 进程名`：查找进程拿到 PID；
>   - `kill PID`：发送 TERM 信号**优雅关闭**（进程可做清理后退出）；
>   - `kill -9 PID`：发送 KILL 信号**强制杀死**（进程无法捕获，慎用）。
> - **Windows**：
>   - `tasklist`：查看当前进程列表（可 `| findstr 进程名` 过滤）；
>   - `taskkill /F /PID 进程PID`：按 PID **强制**杀进程；
>   - `taskkill /IM 程序名.exe`：按程序映像名**批量**杀进程。
>
> **解析**：追问点："kill -9 为什么慎用"——不给进程清理资源的机会，可能留下脏数据/锁文件；优雅关闭优先，无响应才 -9。

### Q2.（简答 ★）Linux 中如何实时查看日志记录？

> **参考答案**：
> - `tail -f app.log`：实时跟踪文件新增内容；
> - 配合 grep 过滤关键字：`tail -f app.log | grep ERROR`，只看目标行；
> - 常用变体：`tail -n 200 app.log`（先看末尾 200 行）、`tail -F app.log`（文件被轮转/重建后仍继续跟踪）。
>
> **解析**：追问点："查找历史日志用哪个命令"——`grep -C 5 'ERROR' app.log`（带上下文）或 `less` 分页浏览；"实时高亮"——`tail -f app.log | grep --color ERROR`。

### Q3.（简答 ★★）SQL 语句中 WHERE 与 HAVING 的区别有哪些？

> **参考答案**：
> 1. **执行顺序**：WHERE 在分组前过滤原始数据；HAVING 在分组聚合后过滤统计结果；
> 2. **聚合函数**：WHERE 不能使用聚合函数；HAVING 专门用来筛选聚合结果（如 `HAVING COUNT(*) > 5`）；
> 3. **使用条件**：WHERE 无需 GROUP BY 即可使用；HAVING 必须搭配 GROUP BY；
> 4. **性能优化**：普通字段条件放 WHERE（先过滤减少参与分组的数据量），聚合过滤放 HAVING，减少分组计算量。
>
> **解析**：一句话总结——**WHERE 过滤"行"，HAVING 过滤"组"**。追问点："能用 WHERE 的条件放 HAVING 会怎样"——结果通常一样但性能差（先聚合后过滤）。

### Q4.（简答 ★）MySQL 常用聚合函数有哪些？各自的作用是什么？

> **参考答案**：
> - **COUNT**：计数；**SUM**：求和；**AVG**：平均值；**MAX**：最大值；**MIN**：最小值。
> - **拓展高频 GROUP_CONCAT**：分组拼接字符串——把分组内多条记录的字段拼接成一个字符串，默认逗号分隔。
>
> ```sql
> -- 按部门分组，展示每个部门所有员工姓名
> SELECT dept_id, GROUP_CONCAT(name) FROM emp GROUP BY dept_id;
> -- 自定义分隔符
> SELECT dept_id, GROUP_CONCAT(name SEPARATOR '|') FROM emp GROUP BY dept_id;
> ```
>
> **解析**：追问点："COUNT(*) 与 COUNT(字段) 的区别"——前者统计行数（含 NULL），后者不统计该字段为 NULL 的行；"GROUP_CONCAT 有长度上限吗"——受 `group_concat_max_len` 限制（默认 1024）。

### Q5.（简答 ★★）Linux 中如何查找文件？给几个常用场景。

> **参考答案**：
> - **按名查找**：`find /app -name "*.log"`（区分大小写）、`-iname`（不区分）；
> - **按类型/大小**：`find /app -type f -size +100M`（找大文件）；`find /app -type d -name logs`；
> - **按时间**：`find /app -mtime -7`（7 天内修改过）；
> - **对结果执行操作**：`find /app -name "*.tmp" -exec rm -f {} \;`；
> - **磁盘占满排查组合**：`df -h` 确认分区满 → `du -sh *` 逐层看目录占用 → `find / -size +1G` 揪出大文件。
>
> **解析**：面试给场景答命令：找配置文件用 `-name`，磁盘排查用 `du` + `find -size`，清理旧日志用 `-mtime`。追问点："find 和 locate 的区别"——locate 查索引库（快，需 `updatedb` 维护，找新文件可能查不到），find 实时遍历磁盘（慢但准）。

### Q6.（简答 ★★）如何查看 Linux 端口是否被占用？占用后怎么处理？

> **参考答案**：
> - `netstat -tunlp | grep 8080`：查看 TCP/UDP 监听与占用进程（经典）；
> - `ss -tunlp | grep 8080`：ss 与 netstat 同源，**速度更快**，新系统首选；
> - `lsof -i:8080`：直接按端口查打开的文件与进程；
> - 处理：从输出拿 PID → `ps -ef | grep PID` 确认是什么进程 → 是预期外进程则 `kill PID`（优雅）/ `kill -9 PID`（强制）释放端口。
>
> **解析**：典型场景是"**服务起不来提示端口占用**"：先查谁占了，确认后杀掉或改服务端口。追问点："netstat 输出里大量 TIME_WAIT 正常吗"——短连接高频的常态，量级过大说明长连接利用不足，需调内核参数或改长连接。

### Q7.（简答 ★★★）线上接口响应异常，请描述用 Linux 命令初步排查的完整流程。

> **参考答案**：
> 一条"**资源 → 进程 → 日志 → 网络 → 磁盘**"的排查链：
> 1. `top`：先看整机 CPU/内存，按 P/M 排序定位异常进程（CPU 100%？内存打满？）；
> 2. `ps -ef | grep 服务名`：确认服务进程存在、启动时间正常（是否被 OOM 杀掉重启）；
> 3. `tail -f app.log | grep -A 10 ERROR`：看应用日志的异常堆栈与时间点；
> 4. `netstat -tunlp | grep 端口`：确认端口在监听、连接数是否异常（大量 SYN/Close_Wait）；
> 5. `df -h`（磁盘）与 `df -i`（inode）：磁盘写满会直接导致日志/接口异常；`free -m` 看内存与交换分区；
> 6. 结论输出：把"哪层出的问题 + 证据"同步给开发/运维定位根因。
>
> **解析**：考察的是**命令组合成排查思路**，不是背单条命令。答题时按流程串讲并说明"每步在排除什么"。追问点："CPU 高怎么继续定位"——`top -Hp <pid>` 看线程，`jstack`（Java）对照找代码热点。

### Q8.（简答 ★★）SQL 中 inner join、left join、right join 的区别？

> **参考答案**：
> 1. **inner join（内连接）**：只返回两表都能匹配上的行；
> 2. **left join（左连接）**：保留左表全部行，右表无匹配的字段填 **NULL**；
> 3. **right join（右连接）**：保留右表全部行，左表无匹配填 NULL（MySQL 不支持 full join，可用 `left join UNION right join` 模拟全外连接）。
>
> 测试场景：**数据一致性核对**——用 `left join ... WHERE b.id IS NULL` 找出"主表有、从表缺失"的脏数据（如订单表有记录但无对应支付流水）。
>
> **解析**：追问点："left join 里 ON 和 WHERE 的区别"——ON 在连接时过滤（不匹配仍保留左表行、填 NULL），WHERE 在连接后过滤（可能把 NULL 行全过滤掉，效果近似 inner join）。

### Q9.（简答 ★★）手写 SQL：查询每个用户的订单总数，只显示订单数大于 10 的用户。

> **参考答案**：
>
> ```sql
> SELECT user_id, COUNT(order_id) AS order_cnt
> FROM orders
> GROUP BY user_id
> HAVING COUNT(order_id) > 10;
> ```
>
> 变体（要显示用户姓名，订单表与用户表分开存）：
>
> ```sql
> SELECT u.user_name, COUNT(o.order_id) AS order_cnt
> FROM user u
> INNER JOIN orders o ON u.user_id = o.user_id
> GROUP BY u.user_id, u.user_name
> HAVING COUNT(o.order_id) > 10;
> ```
>
> **解析**：考点链是"**聚合 → 分组 → HAVING 过滤 → 连表**"，逐级追问是标准套路。追问点："HAVING 能写 WHERE 吗"——条件是聚合结果必须 HAVING，普通字段条件放 WHERE 性能更好。

### Q10.（简答 ★★★）手写 SQL：查询成绩表中第二高的成绩。

> **参考答案**：
>
> ```sql
> -- 方法一：子查询（兼容所有版本）
> SELECT MAX(score) FROM score
> WHERE score < (SELECT MAX(score) FROM score);
>
> -- 方法二：去重排序后跳过第一条（MySQL）
> SELECT DISTINCT score FROM score
> ORDER BY score DESC
> LIMIT 1, 1;
> ```
>
> 注意点：方法二依赖 `DISTINCT` 去重——不去重时并列第一会把"第二高"挤掉；`LIMIT offset, n` 从第 offset+1 条开始取。
>
> **解析**：追问点："load 和 CPU 使用率的区别"——使用率是"忙的比例"，load 是"排队任务数"（含不可中断的 IO 等待），load 高 + CPU 低 = IO 瓶颈的典型指纹；"怎么查是谁"——`top -Hp` + `ps -eo state` 找 D 状态（不可中断 IO）进程。

### Q11.（简答 ★★）top 命令的输出怎么解读？哪些指标最关键？

> **参考答案**：
> - **load average（三个数）**：最近 1/5/15 分钟平均负载——经验值超过 **CPU 核数**即过载（4 核机器 load 8 说明排队严重）；
> - **%CPU**：进程 CPU 占用，按 `P` 排序定位吃 CPU 的进程；`us`（用户态）高 → 应用代码热点，`sy`（内核态）高 → 系统调用频繁，`wa`（IO 等待）高 → 磁盘瓶颈；
> - **%MEM / RES**：内存占用与常驻内存，按 `M` 排序；
> - **`top -Hp <pid>`**：看进程内**线程**级 CPU（配合 jstack 定位代码热点）；
> - 常用交互键：`1` 展开各核、`c` 显示完整命令行、`q` 退出。
>
> **解析**：追问点："load 高但 CPU 不高是什么问题"——大概率 IO 等待（磁盘/网络），看 wa 值与 iostat；"us 和 sy 怎么指导优化"——us 高优化代码（慢 SQL/循环），sy 高查系统调用/上下文切换。

### Q12.（简答 ★★）chmod 命令怎么用？755、644 分别是什么权限？

> **参考答案**：
> 权限三组：**属主/属组/其他**，每组 r=4、w=2、x=1 相加。
> - `chmod 755 file`：rwx r-x r-x——**所有者全权，组和其他人可读可执行**（目录、脚本常用）；
> - `chmod 644 file`：rw- r-- r--——**普通配置文件**常用（所有者可写，其他人只读）；
> - `chmod +x deploy.sh`：给所有者加执行权限；
> - `chown user:group file`：改文件归属；
> - 符号法：`chmod u+x,go-w file`（所有者加执行，组与其他人去写）。
>
> 安全底线：生产文件不轻易 `chmod 777`（任何人都可写，是事故温床）。
>
> **解析**：追问点："为什么脚本必须 +x 才能直接执行"——`./xx.sh` 依赖可执行位，否则用 `sh xx.sh`（解释器代跑不需要 x）；"rwx 对目录的含义"——r 列目录、w 建删文件、x 进入目录。

### Q13.（简答 ★★）df -h 和 du 的区别？磁盘报警时怎么用它们定位？

> **参考答案**：
> - `df -h`：看**文件系统整体**——每个挂载点的总容量/已用/挂载点（回答"哪个分区满了"）；
> - `du -sh /path`：统计**目录实际占用大小**（回答"空间被谁吃了"）；`du -h --max-depth=1 /app` 逐层下钻；
> - **排查流程**：`df -h` 找满的分区 → `du` 逐层定位大目录 → `find /path -size +1G` 揪出大文件或日志 → 确认后清理（先备份）；
> - **经典坑**：`df` 显示满了但 `du` 加起来不大——**文件已删除但进程仍持有句柄**（日志被删但服务没重启），`lsof | grep deleted` 找到进程重启/重开句柄即释放。
>
> **解析**：追问点："df 和 du 结果差异大说明什么"——句柄未释放（上述坑）或挂载点覆盖；"inode 耗尽"——`df -i` 查，海量小文件耗尽 inode，df 看空间却写不进。

### Q14.（简答 ★★）Linux 管道和重定向分别是什么？举几个组合用法。

> **参考答案**：
> - **管道 `|`**：把前一个命令的**标准输出**接到后一个命令的**标准输入**——`cat app.log | grep ERROR | wc -l`（串联处理流）；
> - **重定向**：`>` 覆盖写入、`>>` 追加写入、`2>` 错误输出、`&>` 全部输出、`<` 输入重定向、`/dev/null` 黑洞；
> - 组合示例：
>
> ```bash
> # 统计 ERROR 行数并落盘
> grep -c ERROR app.log > error_count.txt
> # 命令正常输出和报错都丢弃
> some_cmd > /dev/null 2>&1
> # 日志过滤后追加到归档
> tail -n 1000 app.log | grep WARN >> warn_archive.log
> ```
>
> **解析**：追问点："> 与 >> 的区别"——覆盖 vs 追加，写日志归档用 >>；"2>&1 什么意思"——把标准错误（2）重定向到标准输出（1）当前指向处，顺序不能反。

### Q15.（简答 ★）Linux 下压缩与解压文件用什么命令？

> **参考答案**：
> - **tar 打包 + gzip 压缩（最常用）**：
>   - 打包：`tar -czf app.tar.gz /app/logs`（c 创建、z gzip、f 指定文件名）；
>   - 解压：`tar -xzf app.tar.gz -C /target`（x 解压）；
>   - 只看内容不解压：`tar -tzf app.tar.gz`；
> - **zip/unzip**（与 Windows 互通）：`zip -r out.zip dir/`、`unzip out.zip -d /target`；
> - 其他格式：`.gz` 用 `gzip -d / zcat`，`.bz2` 用 `bzip2 -d`。
>
> **解析**：追问点："czf/xzf 各字母含义"——c=create、x=extract、z=gzip、f=file、v=显示过程；"打包和压缩的区别"——tar 是打包（多合一），gzip 是压缩，`tar czf` 一步完成两者。

### Q16.（简答 ★★★）统计日志文件中访问量最高的前 10 个 IP，写出完整命令。

> **参考答案**：
>
> ```bash
> awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -10
> ```
>
> 分步拆解（面试要求讲清每段）：
> 1. `awk '{print $1}'`：取每行第一列（默认按空格切分，日志首列通常是 IP）；
> 2. `sort`：排序——**为 uniq 分组做铺垫**（uniq 只合并相邻行，必须先排）；
> 3. `uniq -c`：相邻去重并计数（输出"次数 IP"）；
> 4. `sort -rn`：按数值逆序排（r 逆序、n 按数字）；
> 5. `head -10`：取前 10。
>
> **解析**：这是"管道组合拳"的经典考题，答出"uniq 为什么要先 sort"就是加分项。追问点："取出现超过 1000 次的 IP"——末尾加 `awk '$1 > 1000'`；"统计 UV/PV"——`sort -u | wc -l` / `wc -l`。

### Q18.（简答 ★★）free -m 的输出怎么解读？buffers 和 cache 有什么区别？

> **参考答案**：
> ```
>        total   used   free   shared  buff/cache  available
> Mem:     15G     3G     2G      0G        10G        12G
> ```
> - **available（12G）才是判断依据**——不是看 free！Linux 把空闲内存拿去做 **buff/cache**（磁盘缓存，需要时可立即回收）；
> - **buffers**：写缓冲（块设备元数据）；**cache**：读缓存（文件内容）——两者都是"可随时回收的内存"；
> - 判断内存紧张：`available` 很低且 swap used 持续增长；
> - 主动释放缓存（测试场景用）：`echo 3 > /proc/sys/vm/drop_caches`（先 sync）。
>
> **解析**：追问点："'内存 used 很高是不是泄漏了'"——先看 available，cache 高是正常现象（Linux 尽量利用内存）；"swap 用了说明什么"——物理内存不足开始换页，性能会明显下降。

### Q19.（简答 ★★）软链接和硬链接的区别？

> **参考答案**：
> - **软链接（符号链接）**：`ln -s target link_name`——**指向路径**的快捷方式；原文件删除后**失效**（悬空链接）；可跨文件系统、可指向目录；有独立 inode；
> - **硬链接**：`ln target link`——**指向同一个 inode**（同一份数据的另一个名字）；删除原文件数据仍在（引用计数归零才真正删除）；不可跨文件系统、不可指向目录；
> - 查看：`ls -li`（i 节点号相同即硬链接；软链接带 `->` 箭头）。
>
> 测试场景：给多版本部署目录做软链接切换（`/app/current -> /app/release-v2.3`），回滚就是改链接。
>
> **解析**：追问点："删了原文件软链接会怎样"——悬空失效（红色闪烁提示）；"硬链接删除的原理"——inode 引用计数减一，归零才真正释放磁盘块；"生产上软链接典型用途"——版本切换/配置指向。

### Q20.（简答 ★★）怎么把本地文件传到远程服务器？说说 scp 和 rsync 的区别。

> **参考答案**：
> - **scp**：`scp file.tar.gz user@10.0.0.5:/app/`（上传）、`scp user@10.0.0.5:/app/a.log ./`（下载）、`-r` 递归目录——简单直接，每次**全量**传输；
> - **rsync**：`rsync -avz /app/logs/ user@10.0.0.5:/backup/logs/`——**增量传输**（只传差异块）、支持断点续传、`--delete` 保持目录镜像、`-a` 保权限时间戳；大目录同步明显更快；
> - 常用：`rsync -avz --exclude='*.log.202*' src/ dst/` 排除规则。
>
> **解析**：追问点："scp 和 rsync 怎么选"——一次性小文件 scp，周期性大目录同步 rsync；"rsync 尾部斜杠的区别"——`/logs/` 传目录内容，`/logs` 会把 logs 目录本身拷过去。

### Q21.（简答 ★★★）uptime 显示 load average: 8.00, 7.50, 7.20，怎么判断负载是否正常？

> **参考答案**：
> - **load average = 处于运行/等待运行状态的任务数均值**（运行中的 + 等待 CPU + 等待 IO 的进程）；
> - **判断基准**：与 **CPU 核数**比较——8 核机器 load=8 说明刚好饱和；**持续 > 核数**即过载，任务在排队；
> - **三个数字的趋势比单值重要**：1 分钟 > 15 分钟 → 负载**正在上升**（突发流量/新问题）；1 分钟 < 15 分钟 → 正在恢复；
> - **归因**：load 高先看 `top`——`us` 高是 CPU 密集（代码/SQL 热点），`wa` 高是磁盘 IO 慢（日志风暴/大量交换），此时 CPU 利用率可能不高但 load 照样高。
>
> **解析**：追问点："load 和 CPU 使用率的区别"——使用率是"忙的比例"，load 是"排队任务数"（含不可中断的 IO 等待），load 高 + CPU 低 = IO 瓶颈的典型指纹；"怎么查是谁"——`top -Hp` + `ps -eo state` 找 D 状态（不可中断 IO）进程。
### Q22.（简答 ★★）DELETE、TRUNCATE、DROP 的区别？

> **参考答案**：
> | 维度 | DELETE | TRUNCATE | DROP |
> | --- | --- | --- | --- |
> | 层级 | DML，删**数据行** | DDL，清空**全部数据** | DDL，删**整张表结构** |
> | WHERE 条件 | 支持（可删部分） | 不支持（只能全清） | — |
> | 速度 | 逐行删，慢（记录 undo） | 快（释放数据页） | 快 |
> | 回滚 | 事务内可 ROLLBACK | 一般不可回滚 | 不可回滚（慎用） |
> | 自增 ID | 保留 | 重置为初始值 | 表都没了 |
>
> 测试场景：压测前重置数据表用 `TRUNCATE`（快且重置自增）；删除符合条件的历史数据用 `DELETE ... WHERE`。
>
> **解析**：追问点："误执行 DROP 怎么补救"——从备份恢复（强调权限管控与操作审计，生产禁用 DROP）；"TRUNCATE 为什么快"——不走逐行删除，直接重置数据页与水位。

### Q23.（简答 ★★）CHAR 和 VARCHAR 的区别？

> **参考答案**：
> - **CHAR(n)**：**定长**——不足 n 位自动补空格到 n，检索时去掉尾部空格；存取快、空间固定；适合长度几乎不变的字段（身份证号、MD5 值用 CHAR(32)）；
> - **VARCHAR(n)**：**变长**——按实际长度存储（额外 1~2 字节记长度）；省空间；适合长度波动大的字段（用户名、地址）；
> - n 的含义：都是**字符数**（MySQL 4.1+ 按 utf8 字符算，不是字节）；
> - 对比常见误区：`int(2)` 与 `int(10)` 的 2/10 只是**显示宽度**（配合 zerofill），不影响存储范围（都是 4 字节）。
>
> **解析**：追问点："CHAR 空间会浪费吗"——定长补齐导致短值浪费空间；"VARCHAR(n) 超长会怎样"——严格模式报错，宽松模式截断+警告（测试要专门验证边界）；"手机号选哪个"——CHAR(11) 长度固定，或 VARCHAR(11) 均可，关键是校验格式。

### Q24.（简答 ★★）数据库三大范式是什么？

> **参考答案**：
> 1. **1NF（原子性）**：每个字段**不可再分**——地址字段拆成省/市/区（或保持整串但不再存"电话1,电话2"）；
> 2. **2NF（完全依赖）**：非主键字段**完全依赖主键**，消除部分依赖——订单明细表（主键=订单ID+商品ID）中"商品名称"只依赖商品ID，应拆到商品表；
> 3. **3NF（直接依赖）**：非主键字段**不传递依赖**主键——员工表存"部门ID"即可，不存"部门名称"（名称依赖部门ID再依赖员工ID）。
>
> 实践态度：范式是**减少冗余、保证一致性**的指导，实际常**反范式**（冗余字段换 JOIN 性能，如订单表冗余商品名快照）。
>
> **解析**：追问点："为什么有时要故意违反范式"——查询性能（少 JOIN）与历史快照需求（订单价格不能随商品改价变化）；"冗余带来的问题"——更新异常（改一处漏多处），需要同步维护机制。

### Q25.（简答 ★★★）什么是索引？什么情况下索引会失效？

> **参考答案**：
> **索引 = 加速查询的数据结构**（MySQL InnoDB 用 B+ 树——树高低、叶子节点存数据且有序，等值与范围查询都快）。
> - **类型**：主键索引（叶子存整行）、二级/普通索引（叶子存主键，需回表）、唯一索引、组合索引、全文索引；
> - **失效场景（高频背诵）**：
>   1. 组合索引不满足**最左前缀**（index(a,b,c) 查 b、c 不走索引）；
>   2. 索引列参与**运算或函数**（`WHERE YEAR(create_time)=2026`）；
>   3. **隐式类型转换**（varchar 列 `WHERE phone=13800001111` 数字比较）；
>   4. `LIKE '%xx'` **前置模糊**（后缀模糊 `'xx%'` 可以走）；
>   5. `OR` 两侧有未加索引的列、`NOT IN / !=`（视选择性，优化器可能全表扫）；
>   6. 优化器判断**全表扫更快**（返回大部分数据时）。
>
> **解析**：验证手段是 `EXPLAIN`（type 至少 range，ref/const 更好）。追问点："组合索引怎么设计"——区分度高的列在前、等值条件在前范围条件在后；"回表是什么"——二级索引拿到主键再回主键索引取整行，覆盖索引（查询列都在索引里）可避免回表。

### Q26.（简答 ★★★）手写 SQL：学生表 student(id, name)、成绩表 score(id, student_id, subject, score)，查询平均分大于 80 的学生姓名和平均分。

> **参考答案**：
>
> ```sql
> SELECT s.name, AVG(sc.score) AS avg_score
> FROM student s
> INNER JOIN score sc ON s.id = sc.student_id
> GROUP BY s.id, s.name
> HAVING AVG(sc.score) > 80
> ORDER BY avg_score DESC;
> ```
>
> 考点链：**join 关联 → GROUP BY 分组 → HAVING 过滤聚合 → ORDER BY 排序**。
>
> 变体追问：
> - "每个学生**每科**成绩（行转列）"：`MAX(CASE WHEN subject='数学' THEN score END) AS math`；
> - "没参加任何考试的学生也要列出来"：INNER JOIN 换 **LEFT JOIN**（NULL 处理）；
> - "平均分前 3 名"：加 `LIMIT 3`（并列则窗口函数 DENSE_RANK）。
>
> **解析**：写 SQL 时把表别名、字段名写语义化（不写 `t1/t2`、不写 SELECT *）。追问点："GROUP BY 里的 name 能不能省"——`ONLY_FULL_GROUP_BY` 模式下非聚合列必须出现在 GROUP BY。

### Q27.（简答 ★★）LIMIT 分页怎么写？深分页有什么问题怎么优化？

> **参考答案**：
> - 基本语法：`SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 10000`（或 `LIMIT 10000, 20`——从第 10001 条起取 20 条）；
> - **深分页问题**：MySQL 需要扫描并丢弃前 10000 行——页码越深越慢，`LIMIT 1000000, 20` 直接拖垮 DB；
> - **优化方案**：
>   1. **游标/键集分页**（首选）：记录上一页最大 id，`WHERE id > 1000000 ORDER BY id LIMIT 20`（索引直达，恒定快）；
>   2. **延迟关联**：`SELECT * FROM orders o JOIN (SELECT id FROM orders ORDER BY id LIMIT 1000000, 20) t ON o.id = t.id`——先在覆盖索引上翻页，再回表取 20 行；
>   3. 产品侧限制：禁止跳到很深的页（搜索页通常只给前 100 页）。
>
> **解析**：追问点："为什么游标分页快"——利用索引定位直接跳到起始点，不扫描前序行；"ORDER BY 无索引会怎样"——filesort 全量排序，深分页雪上加霜。

### Q28.（简答 ★★★）什么是事务？事务的 ACID 特性分别指什么？

> **参考答案**：
> **事务 = 一组不可分割的 SQL 操作单元**，要么全部成功要么全部回滚（典型：转账 = 扣款 + 入账）。
> - **A 原子性（Atomicity）**：全部成功或全部失败，不存在中间状态（undo log 实现回滚）；
> - **C 一致性（Consistency）**：事务前后数据满足业务约束（总余额不变、库存不为负）——是最终目的，由 A/I/D 共同保障；
> - **I 隔离性（Isolation）**：并发事务互不干扰（由锁 + MVCC 实现，分级见下一题）；
> - **D 持久性（Durability）**：提交后数据落盘不丢（redo log 先写日志再刷数据页）。
>
> 测试场景：转账类接口的并发测试——并发 100 笔转账后对账"总额守恒"；故意在事务中间制造异常验证回滚完整性。
>
> **解析**：追问点："C 和其他三个的关系"——A/I/D 是手段，C 是目的；"怎么验证原子性"——双写操作中手动中断（kill 会话/抛异常），查库确认两边都未生效。

### Q29.（简答 ★★★）MySQL 的事务隔离级别有哪些？脏读、不可重复读、幻读分别是什么？

> **参考答案**：
> 并发问题三件套：
> 1. **脏读**：读到别的事务**还没提交**的数据（对方回滚了，你读到的就是假数据）；
> 2. **不可重复读**：同一事务内两次读同一行，**内容变了**（别人 UPDATE 并提交了）；
> 3. **幻读**：同一事务内两次**范围查询**，**行数变了**（别人 INSERT 并提交了）。
>
> 四个隔离级别（从严到松）：
> | 级别 | 脏读 | 不可重复读 | 幻读 |
> | --- | --- | --- | --- |
> | 读未提交 RU | 有 | 有 | 有 |
> | 读已提交 RC（Oracle 默认） | 无 | 有 | 有 |
> | **可重复读 RR（MySQL 默认）** | 无 | 无 | InnoDB 基本避免（间隙锁） |
> | 串行化 | 无 | 无 | 无（性能差） |
>
> InnoDB 通过 **MVCC（多版本快照读）+ 锁** 实现 RR：普通 SELECT 走快照不加锁，当前读（UPDATE/SELECT FOR UPDATE）加行锁与间隙锁。
>
> **解析**：追问点："不可重复读和幻读的区别"——前者同一行**值**变（update），后者结果集**行数**变（insert）；"RR 级别怎么防幻读"——快照读靠 MVCC 版本链，当前读靠临键锁（Next-Key Lock）锁区间。

### Q30.（简答 ★★★）表里有重复数据，如何找出重复记录并删除只保留一条？

> **参考答案**：
>
> ```sql
> -- 1. 找出重复的（按 name 重复）
> SELECT name, COUNT(*) AS cnt
> FROM user
> GROUP BY name
> HAVING COUNT(*) > 1;
>
> -- 2. 删除重复只保留 id 最小的一条
> DELETE FROM user
> WHERE id NOT IN (
>     SELECT min_id FROM (
>         SELECT MIN(id) AS min_id FROM user GROUP BY name
>     ) t
> );
> ```
>
> 要点：**先查后删**（生产删除前必须先 SELECT 确认范围）；MySQL 不允许直接对子查询目标表 DELETE，需要包一层临时表（`t`）。
>
> 进阶写法（8.0 窗口函数，更直观）：
>
> ```sql
> DELETE FROM user WHERE id IN (
>     SELECT id FROM (
>         SELECT id, ROW_NUMBER() OVER (PARTITION BY name ORDER BY id) AS rn
>         FROM user
>     ) t WHERE rn > 1
> );
> ```
>
> **解析**：追问点："为什么 rn > 1 表示重复"——ROW_NUMBER 给每组重复按 id 排序，>1 的都是非首个；"删除前必须做什么"——备份（`CREATE TABLE bak AS SELECT ...`）+ 确认 WHERE 范围。
