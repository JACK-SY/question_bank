> **本章 19 题**：以 HTTP/RESTful 接口为基准，工具示例用 Postman；联调与偶现问题排查（Q17/Q18）是中高级面试加分题。

### Q1.（单选 ★★）按 HTTP 语义，下列哪组方法具备幂等性？

- A. GET、POST
- B. GET、PUT、DELETE
- C. POST、PATCH、PUT
- D. 仅 GET

> **答案**：B
> **解析**：**幂等 = 同一请求执行一次与执行多次效果相同**。GET 天然幂等；PUT 幂等（整体替换，重复提交结果一致）；DELETE 幂等（删除已不存在的资源仍返回同样语义）；**POST 不幂等**（重复提交可能创建多笔订单）。接口测试考点：对支付/下单类 POST 接口必须设计"重复提交防重"用例。

### Q2.（简答 ★★）cookie、session、token 三者的区别？

> **参考答案**：
> 1. **cookie**：存储在**客户端**，随同域请求自动携带，可被用户查看与篡改，一般存非敏感状态。
> 2. **session**：状态存在**服务端**，客户端只持 session id（通常借 cookie 传递）；服务有状态，分布式下需要 session 共享（粘性会话或集中存储）。
> 3. **token（如 JWT）**：自包含令牌，**服务端无状态**——签名保证不可篡改，payload 携带用户信息，天然适合分布式与多端；代价是签发后无法主动作废（需黑名单机制）。
> 4. 安全设计：cookie 加 HttpOnly/Secure/SameSite，token 设过期时间与刷新机制，敏感接口走 HTTPS。
>
> **解析**：答题线索是"**存哪、谁管状态、能否篡改**"。追问点：JWT 为什么能防篡改（签名防改，但明文可见，别放敏感信息）。

### Q3.（单选 ★）接口返回 401 与 403 的区别是？

- A. 都表示服务器内部错误
- B. 401 未认证（没登录或凭证失效），403 已认证但无权限
- C. 401 已认证但无权限，403 未认证
- D. 404 的别名

> **答案**：B
> **解析**：**401 Unauthorized = 你是谁？（认证失败）**；**403 Forbidden = 我知道你是谁，但你不能干这个（授权失败）**。设计用例时两者分开断言：未带 token → 401，带普通用户 token 访问管理员接口 → 403。常见 4xx：400 参数错误、401 未认证、403 无权限、404 资源不存在、429 限流。

### Q4.（简答 ★★★）设计一个"新增收货地址"接口的测试用例，你会覆盖哪些维度？

> **参考答案**：
> 1. **功能正确性**：合法参数新增成功，返回字段与库中数据一致。
> 2. **必填校验**：逐个去掉必填字段（缺姓名、缺电话、缺地址）。
> 3. **格式校验**：手机号 11 位规则、超长字符串、特殊字符/emoji、前后空格。
> 4. **边界值**：地址字段长度上下界（按规格）、收货地址数量上限（如满 20 条再新增）。
> 5. **异常流**：未登录 token 失效 → 401；无权限用户 → 403；重复快速提交（幂等/防重）。
> 6. **安全**：SQL 注入、XSS 脚本入库回显、越权（改别人地址 id）、敏感信息脱敏。
> 7. **状态与联动**：新增后列表刷新、设为默认地址的唯一性约束。
>
> **解析**：接口用例设计万能框架 = **参数校验（必填/格式/边界）→ 业务规则 → 异常与状态码 → 安全 → 幂等/并发 → 关联影响**。对照需求文档逐项落地才是得分点。

### Q5.（简答 ★★★）登录接口的测试点有哪些？

> **参考答案**：
> 1. **正常登录**：正确账号密码，返回 token/cookie 及用户信息结构正确。
> 2. **凭证校验**：错误密码、不存在账号、禁用/注销账号、大小写敏感、空值。
> 3. **安全策略**：连续错误 N 次锁定与解锁、验证码校验与刷新、错误提示不泄露账号是否存在、密码不回显、防爆破限流（429）。
> 4. **注入与篡改**：SQL 注入、超长密码、token 篡改后访问受保护接口。
> 5. **会话管理**：token 过期与刷新、多端登录互踢策略、登出后 token 失效。
> 6. **接口层面**：请求方法约束（GET 登录是反模式）、错误码区分（400/401）、响应时间。
>
> **解析**：登录是接口面试的"标准考题"，亮点在于**错误提示不泄露账号是否存在**与**防爆破限流**两个安全点。

### Q6.（单选 ★★）Postman 中 B 接口需要 A 接口返回的 token，标准做法是？

- A. 手动复制 token 粘贴到 B 的 Header
- B. 在 A 的 Tests 脚本中 `pm.environment.set('token', pm.response.json().token)`，B 的 Header 引用 `{{token}}`
- C. 用两个独立的 Collection 分别跑
- D. 把 token 写死在 URL 里

> **答案**：B
> **解析**：接口关联（参数传递）三板斧：**Tests/后置脚本提取 → 环境变量/集合变量存储 → `{{变量}}` 引用**。进阶：Pre-request Script 处理签名/时间戳；Newman + CI 跑集合实现接口自动化回归。追问点：environment 与 collection variable 的作用域差异。

### Q7.（单选 ★★）接口测试中处理接口间数据依赖（下单接口依赖登录态 + 收货地址 ID）的最佳实践是？

- A. 每个接口用例都用固定写死的测试账号数据
- B. 用前置接口获取数据后通过变量传递，用例保持独立可重复执行
- C. 跳过依赖接口直接猜参数
- D. 只测试不依赖其他接口的接口

> **答案**：B
> **解析**：核心原则：**用例自准备前置数据**（setup 建数据 → 执行 → teardown 清理），保证可重复执行、环境无关。实现上：前置请求链 + 变量传递，或直接调 DB/API 造数。A 的写死数据在并行执行与数据变更下必挂；工程上通常封装"造数服务"统一管理测试数据生命周期。

### Q8.（简答 ★★）GET 和 POST 的区别是什么？

> **参考答案**：
> - **GET**：浏览器默认缓存，相同 URL 再次访问直接读缓存，可通过 `Cache-Control` 控制缓存行为；参数拼在 URL 上，长度受限、会被历史记录/日志留存。
> - **POST**：浏览器默认不缓存，每次都会重新发起请求；参数在请求体中，相对不易被缓存与留存。
> - 面试补充：语义上 GET 是幂等的获取资源，POST 是提交数据创建/处理资源；安全性都一般（HTTP 明文下 GET 参数可见，POST 报文体也可抓包），敏感数据走 HTTPS。
>
> **解析**：追问点："GET 一定幂等吗"——按 HTTP 语义是，但业务实现未必（如 GET 触发统计计数）；"GET 能带 body 吗"——协议不禁止但约定俗成不带。

### Q9.（简答 ★）HTTP 常见的响应状态码有哪些？各自含义是什么？

> **参考答案**：
> - **200**：请求成功
> - **304**：资源未变化，走本地缓存
> - **400**：客户端参数错误
> - **401**：未登录 / token 失效
> - **403**：已登录但权限不足
> - **404**：接口/资源不存在
> - **405**：请求方法不匹配（如对 POST 接口发了 GET）
> - **500**：服务端代码报错
> - **502 / 503**：网关收到无效响应 / 服务不可用（服务挂了）
> - **504**：后端接口超时
>
> **解析**：记忆分组——2xx 成功、3xx 缓存/重定向、4xx 客户端错误、5xx 服务端错误；401 与 403 的区别是高频追问（见本章 Q3）。

### Q10.（简答 ★★）HTTPS 请求安全吗？为什么抓包工具（Fiddler/Charles）能抓到 HTTPS 明文参数？

> **参考答案**：
> - HTTPS 在正常场景下是安全的：传输层用 TLS 加密，**直接抓网卡流量只能看到密文**，无法解析内容。
> - 抓包工具能抓到明文，本质是**中间人（MITM）**：需要先在系统/浏览器安装抓包工具的**自签名根证书**，此后工具充当中间人——
>   1. 与**客户端**建立 TLS 连接（使用自己伪造的证书，因根证书已信任而通过校验）；
>   2. 再与**真实服务端**建立另一条 TLS 连接；
>   3. 两个连接之间的数据在工具内以明文中转，即可查看/修改。
> - 结论：HTTPS 安全的前提是**证书校验有效**；App 端可开启 SSL Pinning（证书锁定）防中间人抓包。
>
> **解析**：答题亮点是主动补上"如何防"：证书锁定、检测代理、双向认证。追问点："抓 HTTPS 浪费流量的说法对吗"——错，加密的是内容，流量特征仍可见。

### Q11.（简答 ★★★）如何保证自动化用例覆盖率是真实的，而不是同一个接口换几个参数反复跑凑出来的？

> **参考答案**：框架做三层闭环：
> - **断言分层**：核心接口做全字段断言，非核心接口简化校验——保证每条用例有真实校验强度，而不是"跑过=通过"。
> - **覆盖度量**：对接接口文档（Swagger 等）自动对比字段与接口清单，统计**断言覆盖率**（被有效断言覆盖的字段占比）而非"用例数量"，对未覆盖接口/字段主动预警。
> - **CI 闭环**：打通 CICD，代码提交自动触发分层回归（冒烟 → 核心回归 → 全量），异常阻断合并上线。
>
> **解析**：这题考的是"指标是否可被游戏化"的意识。关键词：**按接口/字段维度统计、断言强度量化、文档比对找漏测**——换参数重复跑不会提高字段覆盖率，凑数自然现形。

### Q12.（简答 ★★）如何模拟弱网环境进行接口测试？

> **参考答案**：
> - **网络限速工具**：
>   1. **Charles Proxy（跨平台）**：设置带宽限制（如模拟 3G 网络速度）；模拟高延迟和丢包率；支持断点续传等复杂场景。
>   2. **Fiddler（Windows）**：Throttling 功能可配置各种网络条件；可自定义规则控制请求响应时间。
>   3. **浏览器开发者工具（Chrome/Firefox）**：DevTools 内置 Network Throttling——`Network tab → Online 下拉 → Fast 3G / Slow 3G / Custom` 自定义上下行速率与延迟。
>   4. **移动端补充**：iOS 用系统开发者选项 **Network Link Conditioner**；Android 可用模拟器网络速率配置或抓包工具代理手机流量。
> - **弱网下重点验证什么**（工具只是手段，验证点才是得分项）：
>   - 超时与重试机制是否生效，超时提示是否友好；
>   - 弱网下的**重复提交/幂等**（下单、支付防重）；
>   - 加载占位与进度反馈、断线重连后的数据恢复与一致性；
>   - 请求失败的兜底文案与降级逻辑。
>
> **解析**：答题结构"**工具选型 + 验证点**"两段式。追问点："Charles 模拟弱网的原理"——代理层对响应做延迟/限速转发；"弱网测试与断网测试的区别"——断网测离线与重连，弱网测慢速下的体验与容错。

### Q13.（简答 ★★★）如何在 JMeter 中处理需要加密的请求参数？

> **参考答案**：
> 核心思路：用 **JSR223 PreProcessor（或 JSR223 Sampler）编写 Groovy 脚本**完成加密，通过 `vars` 变量把密文传给 HTTP 请求。具体步骤：
> 1. 添加 **HTTP Request** 元件，配置目标 URL 与请求方法；
> 2. 在其子元素中添加 **JSR223 PreProcessor**，语言选 **Groovy**；
> 3. 在脚本区编写加密逻辑：先 `vars.get()` 取原始参数，加密后再 `vars.put()` 存回变量；
> 4. HTTP Request 的参数值用 `${variableName}` 引用加密后的变量。
>
> 以 Base64 编码为例：
>
> ```groovy
> import org.apache.commons.codec.binary.Base64
>
> // 获取原始参数
> def originalParameter = vars.get("originalParameter")
> // 对参数进行 Base64 编码
> def encodedParameter = Base64.encodeBase64String(originalParameter.bytes)
> // 将编码后的参数设置为 JMeter 变量
> vars.put("encodedParameter", encodedParameter)
> ```
>
> 然后在 HTTP Request 中把请求参数值设置为 `${encodedParameter}`。
>
> - **常见加密场景的处理**：
>   - **MD5/SHA 签名**：用 `MessageDigest` 对"参数按 key 排序拼接 + 时间戳 + secretKey"计算摘要，多参数接口注意与服务端约定拼接规则；
>   - **AES/DES 加解密**：脚本内用 `javax.crypto` 完成加解密，key/iv 可参数化；
>   - **调用已有加密逻辑**：把开发提供的加解密工具类打成 jar 放入 `jmeter/lib`，脚本中直接 `import` 调用，避免重复实现导致口径不一致；
>   - **参数化配合**：原始参数可来自 CSV Data Set Config / 用户定义变量，加密脚本逐次迭代取值，实现"每个虚拟用户用不同数据加密"。
>
> **解析**：答题结构"**核心机制 + 四步操作 + 代码示例 + 场景扩展**"。追问点："为什么推荐 JSR223 + Groovy 而不是 Beanshell"——Groovy 编译执行性能好、支持缓存，Beanshell 解释执行易成瓶颈；"签名参数怎么组织"——排序拼接规则、时间戳防重放、nonce 唯一性；"加密后怎么断言"——服务端返回密文时可在 JSR223 PostProcessor 解密后再做断言。

### Q14.（简答 ★★）接口测试中什么是 Mock？什么场景下需要？

> **参考答案**：
> **Mock = 用一个"桩服务"替代真实的下游接口/未完成的接口**，按预设契约返回模拟响应，解除测试对依赖方的阻塞。
> - **典型场景**：
>   1. 被测功能依赖的**第三方/下游接口未就绪**（开发中、联调排期冲突）；
>   2. **构造难以真实出现的响应**——超时、500、余额不足等异常码（真实环境很难造）；
>   3. **性能测试隔离**——mock 掉非关注依赖，避免下游瓶颈污染压测数据；
>   4. 依赖第三方收费接口，避免测试消耗真实额度。
> - **常用工具**：Python Flask / FastAPI 几十行起一个 mock 服务；Postman Mock Server；JVM 系常用 Moco。
>
> **解析**：追问点："mock 响应怎么保证真实"——与开发约定接口契约（schema/示例报文），字段结构对齐真实实现；"mock 的风险"——mock 通过≠联调通过，契约变更后 mock 未同步会造成假绿，需定期用真实环境回归。

### Q15.（简答 ★★）如何在 JMeter 中测试文件上传接口？

> **参考答案**：
> 1. HTTP Request 的 Method 选 **POST**，勾选 **Use multipart/form-data**（上传即 multipart 类型，不能选 Body Data）；
> 2. 在 **Files Upload** 面板配置三要素：**文件路径**（可由 CSV 参数化 `${filePath}`）、**参数名**（与服务端约定的字段名，如 `file`）、**MIME 类型**（如 `image/png`）；
> 3. 其余业务参数放同名 Parameters 表格中（multipart 可同时携带表单字段）；
> 4. 断言响应码与返回的文件 URL，必要时 `GET` 回传文件做**内容比对**（大小/hash）。
>
> **测试关注点**（除正常流程）：超大文件、0 字节文件、格式不符、并发上传同名文件、断网中断续传。
>
> **解析**：追问点："上传接口压测注意什么"——注意磁盘 IO 与带宽是共享瓶颈，压测机与服务器都要监控；"下载接口怎么断言"——响应字节大小、文件 md5 与源文件对比。

### Q16.（简答 ★★）TCP 三次握手和四次挥手的过程？为什么握手三次、挥手四次？

> **参考答案**：
> - **三次握手（建立连接）**：客户端发 `SYN` → 服务端回 `SYN+ACK` → 客户端再回 `ACK`，连接建立。**三次的原因**：确认双方的收发能力都正常（第二次确认服务端能收能发，第三次确认客户端能收）；同时防止**历史失效的连接请求**突然到达服务端造成资源浪费。
> - **四次挥手（断开连接）**：主动方发 `FIN` → 被动方回 `ACK` → 被动方（数据发完后）再发 `FIN` → 主动方回 `ACK`。**四次的原因**：收到 FIN 时被动方**可能还有数据没发完**，所以 ACK（"我知道了"）和 FIN（"我也发完了"）分开发送。
> - **TIME_WAIT**：主动关闭方最后停留 2MSL 的状态，确保最后的 ACK 能重传；服务端出现**大量 TIME_WAIT** 说明短连接过多。
>
> **测试场景**：抓包（Wireshark/tcpdump）分析建连耗时定位慢请求；排查 502 时看后端连接状态。
>
> **解析**：追问点："为什么 TIME_WAIT 要等 2MSL"——确保最后的 ACK 可达 + 让旧连接报文在网络中消亡，避免污染新连接；"HTTP 的 keep-alive 和 TCP 握手的关系"——keep-alive 复用已握手的 TCP 连接发多个 HTTP 请求，减少握手开销。

### Q17.（简答 ★★★）多接口联调测试的核心难点是什么？如何保证测试数据的一致性？

> **参考答案**：
> 1. **核心难点**：
>    - **依赖链长**：上游接口的输出是下游的输入，任一环节阻塞或变更都会卡住整条链路；
>    - **环境与数据不一致**：多个服务的测试环境版本/配置不齐；数据经多个服务落库与转换，字段口径易偏差；
>    - **问题定位难**：链路失败可能是任一参与方的 bug，容易"扯皮"；
>    - **进度协同**：各团队排期不同，接口就绪时间对不齐。
> 2. **保证数据一致性的做法**：
>    - **统一造数入口**：测试数据经统一的"造数服务/API"创建，各服务消费同一份主数据，不各自手工插库；
>    - **用例自备数据 + 自动清理**：setup 建数 → 执行 → teardown 清理，保证可重复执行；
>    - **契约先行**：联调前以接口文档/Schema 约定字段与格式，Mock 按契约返回；契约变更走评审并同步所有消费方；
>    - **断言下沉到数据层**：不仅断言接口返回，还到 DB/缓存核对各服务落库结果一致（对账思维）；
>    - **全链路 traceId**：日志按 traceId 串联，出问题沿调用链还原数据流转路径。
>
> **解析**：答题框架 = "难点（依赖、环境、定位、协同）+ 手段（统一造数、契约、对账、链路）"。追问点："联调出 bug 扯皮怎么办"——用 traceId + 各服务日志时间线定位第一现场，数据说话；"联调和单接口自动化的区别"——联调重点在多服务集成的数据流，单接口自动化重点在单接口契约。

### Q18.（简答 ★★★）接口测试中返回结果不稳定（偶现成功/失败），你会如何排查？

> **参考答案**：
> 按"**收集证据 → 分类 → 定位 → 收敛**"四步，偶现问题不靠猜、靠证据链：
> 1. **收集证据**：保存失败时的完整请求/响应报文、traceId、时间戳；先确认请求参数完全一致（排除参数化数据不同的干扰）；
> 2. **分类现象**：偶现超时/5xx → 偏环境与容量问题；偶现业务校验失败/数据不对 → 偏数据与并发时序问题；
> 3. **逐层排查常见根因**：
>    - **环境**：多节点负载均衡下某节点版本/配置不一致（部分请求打到坏节点）、服务发布重启中；
>    - **数据**：脏数据残留、用例并发修改同一测试数据、缓存与 DB 不一致（读到旧缓存）；
>    - **时序/并发**：异步处理未完成就断言（下单后立刻查订单，落库没完成）、重复提交与幂等、竞态条件；
>    - **依赖**：下游/三方接口限流或抖动，重试后成功；
>    - **资源**：连接池偶发打满、GC 停顿、网络抖动；
> 4. **定位手段**：固定参数反复重放提高复现率；diff 成功/失败两份响应的差异字段；按 traceId 对齐各服务日志时间线；强制路由单节点验证；
> 5. **收敛验证**：针对假设定向复现（并发放大、锁节点），修复后加监控防复发。
>
> **解析**：得分点是"报文 + traceId + 时间线"三件套。追问点："怎么提高复现概率"——固定参数重放、并发放大、锁定单节点；"偶现问题要不要提 bug"——要提，注明复现概率与已收集的证据。

### Q19.（简答 ★★★）如何设计接口的异常测试用例？举例说明。

> **参考答案**：
> 异常用例按"**参数异常 → 状态与权限异常 → 数据与环境异常**"三层展开：
> 1. **参数异常**：必填字段缺失/传空/null；格式非法（手机号 12 位、金额传负数）；边界（字符串超长、数组为空、分页超出范围）；类型篡改（数字字段传字符串、多传未定义字段，验证是 400 还是忽略）；
> 2. **状态与权限异常**：未登录/token 过期/伪造 token → 401；越权访问他人资源（横向越权）、普通用户调管理员接口（纵向越权）→ 403；资源 id 不存在/已删除 → 404；重复提交重放 → 防重校验；
> 3. **数据与环境异常**：业务规则冲突（库存为 0 下单、余额不足支付）；依赖异常（第三方接口超时/报错时被测接口的容错，可用 Mock 构造）；弱网断网、请求超时中断；限流（429）与降级表现。
>
> 举例（新增收货地址）：不带 token → 401；phone 传 "abc" → 400 参数错误；把 body 中的 user_id 改成他人 → 403 越权拦截；address 传 1 万字符 → 边界处理；库存商品并发下单 → 防超卖。
>
> **解析**：异常用例的设计依据是**需求的错误处理约定 + 状态码语义**；断言不只是"报错了"，要断言错误码、错误信息（不泄露堆栈/内部细节）、以及异常数据不落库。追问点："异常场景怎么批量自动化"——参数化数据驱动生成非法参数 + Mock 构造依赖异常。
