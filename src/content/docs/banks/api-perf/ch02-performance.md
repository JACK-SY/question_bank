> **本章 32 题**：性能测试简答题重点看"指标口径"与"瓶颈定位思路"两个框架；场景题（秒杀/缓存/慢 SQL）按"现象→定位→措施"三段作答。

### Q1.（多选 ★）性能测试关注的核心指标包括？

- A. 响应时间（RT）
- B. 吞吐量（TPS/QPS）
- C. 并发用户数
- D. 服务器资源利用率（CPU/内存/IO）与错误率

> **答案**：ABCD
> **解析**：全选。答题时按**客户端视角**（RT、吞吐、并发、错误率）与**服务端视角**（CPU、内存、磁盘 IO、网络带宽、JVM GC）分层陈述，体现体系化。每个指标都要有达标线（如"RT P99 < 500ms，错误率 < 0.1%"）——性能验收从来都是指标化验收。

### Q2.（单选 ★★）TPS 与 QPS 的区别是？

- A. 完全相同
- B. QPS 是每秒查询次数（接口级）；TPS 是每秒完成的事务数，一个事务可能包含多个请求/查询
- C. TPS 一定小于 QPS
- D. QPS 只用于数据库

> **答案**：B
> **解析**：**QPS 面向"查询/请求"，TPS 面向"业务事务"**：下单事务 = 登录态校验 + 库存查询 + 创建订单 3 个请求，则 TPS ≈ QPS/3（视场景）。性能报告里必须写清口径，否则数据没法横向比较。C 不成立：单请求事务时两者相等。

### Q3.（简答 ★★）负载测试、压力测试、稳定性测试、尖峰测试分别验证什么？

> **参考答案**：
> 1. **负载测试（Load）**：按预期峰值负载（如日常 3 倍）施压，验证系统能否达标——"**预期内扛不扛得住**"。
> 2. **压力测试（Stress）**：持续加压超过预期直到系统出错，找**系统极限容量与失效方式**——"极限在哪、怎么挂的"。
> 3. **稳定性测试（Soak/Endurance）**：中等负载长时间运行（如 7×24h），暴露内存泄漏、连接泄漏、日志膨胀等问题。
> 4. **尖峰测试（Spike）**：流量瞬间陡增陡降（秒杀、整点活动），验证弹性伸缩与恢复能力。
>
> **解析**：答题锚点 = **目标不同**：达标 / 找极限 / 找慢性病 / 找弹性。面试常追问"秒杀场景测什么"——尖峰 + 限流 + 库存一致性。

### Q4.（简答 ★★）简述一次完整的性能测试流程。

> **参考答案**：
> 1. **需求分析**：明确测什么接口/链路、目标指标（RT/TPS/错误率）、生产流量模型（从监控取数）。
> 2. **方案设计**：环境（尽量生产等比）、数据量级、加压模型（梯度/阶梯）、监控项。
> 3. **脚本与数据准备**：参数化、关联、思考时间（模拟真实用户节奏）。
> 4. **执行**：先单基准（单用户 RT 基线）再梯度加压，每轮记录指标。
> 5. **监控**：压测端 + 网关 + 应用（线程池/GC）+ 中间件（连接池/缓存）+ DB（慢 SQL/锁）+ 主机资源，全链路对齐时间线。
> 6. **分析与调优**：定位瓶颈 → 优化 → 复测，闭环。
> 7. **报告**：结论先行（是否达标）、容量结论（单机/集群容量）、风险与建议。
>
> **解析**：高频追问"你怎么确定加多少压"——从生产监控取峰值 QPS，按目标容量乘安全系数设计梯度。

### Q5.（单选 ★★）用户感知的"接口响应时间"由哪几部分构成？

- A. 仅服务器处理时间
- B. 网络传输时间 + 服务端处理时间（含中间件与 DB），端到端
- C. 仅数据库查询时间
- D. 浏览器渲染时间

> **答案**：B
> **解析**：端到端 RT = **请求网络耗时 + 服务端链路处理耗时（应用/缓存/DB）+ 响应网络耗时**。测试时区分客户端视角 RT 与服务端日志耗时，两者差值 = 网络与传输开销；外场优化（CDN、压缩）与服务内优化（慢 SQL、GC）要分开治。

### Q6.（简答 ★★★）压测中并发 200 时 RT 从 200ms 飙到 2s，CPU 仅 60%，你的排查思路？

> **参考答案**：
> 1. **CPU 不高却慢 → 等待型瓶颈**，重点查"卡在哪等"：
>    - **DB 层**：慢 SQL、锁等待、连接池耗尽（`show processlist`、慢查询日志、连接池监控）。
>    - **应用层**：线程池打满/队列堆积、GC 频繁停顿（GC 日志、full GC 次数）、锁竞争。
>    - **外部依赖**：下游 RPC/缓存/三方接口 RT、超时与重试风暴。
> 2. **对齐时间线**：把各层监控按同一时间轴对照，找 RT 陡增的"第一现场"。
> 3. **缩小范围**：网关日志看哪段链路慢（全链路追踪 traceId）→ 定位到具体接口与 SQL。
> 4. **验证假设**：单独压 DB、单独压应用，剥离变量。
> 5. 修复后**复测对照**，确认 RT 恢复且容量达标。
>
> **解析**：评分关键词：**不全信 CPU（瓶颈常在 IO/等待）、全链路监控、时间线对齐、变量剥离**。补充：错误率与 RT 要一起看，高 RT 常伴随超时重试放大流量。

### Q7.（多选 ★）JMeter 中下列组件的作用配对正确的是？

- A. 线程组（Thread Group）——模拟并发用户
- B. 断言（Assertion）——校验响应是否符合预期
- C. 监听器（Listener）——收集与展示结果（聚合报告、结果树）
- D. 定时器（Timer）——控制请求发送节奏/思考时间

> **答案**：ABCD
> **解析**：全对。补充高频组件：CSV Data Set Config（参数化）、JSON Extractor/正则提取器（关联）、前置/后置处理器（脚本逻辑）、HTTP 请求默认值（环境切换）。实操要点：跑性能时监听器只留聚合报告（GUI 附加开销影响数据准确性，正式压测用 CLI 模式 + 结果文件离线分析）。

### Q8.（简答 ★★）并发用户数和在线用户数的区别？

> **参考答案**：
> - **在线用户数**：已登录且保持会话的用户总量，但**不一定在发起请求**（页面停留、看内容）；
> - **并发用户数**：**同一时刻**真正向服务器发起请求的用户数量，直接产生服务器压力。
>
> 关系：在线数 ≫ 并发数（同一时刻只有部分用户在操作，通常按 5%~20% 估算）。压测容量估算常用：**并发 ≈ 日活 × 人均请求次数 ÷ 当日秒数 × 峰值系数**，再结合业务高峰（如整点秒杀）修正。
>
> **解析**：追问点："思考时间对并发的影响"——加思考时间会降低单用户请求频率，相同线程数下系统压力更接近真实用户；不加思考时间则是"野蛮压"，测的是极限容量而非真实业务场景。

### Q9.（简答 ★★★）TPS 随并发数增加的变化规律是什么？什么是系统拐点？

> **参考答案**：
> 以"逐步加压"为线索描述：
> 1. **轻载区**：资源未饱和，TPS 随并发数**近似线性增长**，响应时间（RT）平稳；
> 2. **拐点（最佳并发区间）**：某类资源（CPU/连接池/锁）开始饱和，TPS 增长放缓、RT 开始上升——**TPS 最高且 RT 可接受**的区间即系统最佳吞吐能力；
> 3. **过载区**：继续加压，线程/连接排队加剧，TPS 不升反降，RT 快速恶化（甚至超时雪崩）。
>
> 实践结论：**容量定位找拐点**——拐点对应的并发数就是该系统生产容量规划的依据，而不是"压得越高越好"。
>
> **解析**：追问点："并发数、TPS、RT 的换算关系"——并发数 ≈ TPS × RT（单位秒）；"RT 突然从 50ms 涨到 3s 但 TPS 不变说明什么"——请求在排队，瓶颈在资源（线程池/连接池/锁），不在吞吐能力本身。

### Q10.（简答 ★★）JMeter 中有哪些参数化方式？

> **参考答案**：
> 1. **CSV Data Set Config**（首选）：从文件批量读数据（登录账号、测试商品），支持多虚拟用户各取各行；
> 2. **用户定义的变量**：全局静态变量，适合 URL 域名、环境配置；
> 3. **用户参数（User Parameters）**：线程组内多组值轮询，适合小数据量；
> 4. **函数助手**：`__Random`、`__UUID`、`__time`（时间戳）、`__counter`（计数器）；
> 5. **Random Variable**：生成随机数字变量。
>
> CSV 关键配置：**文件编码**（中文用 UTF-8）、**Recycle on EOF**（读完是否重读）、**Sharing mode**（所有线程共享还是线程独立）。
>
> **解析**：追问点："参数化和关联的区别"——参数化的数据**预置在外部文件**，关联的数据来自**上游接口响应**，两者常组合（上游提取 token + CSV 提取业务数据）。

### Q11.（简答 ★★★）JMeter 中下一个接口要用上一个接口的返回值，怎么做关联？

> **参考答案**：
> 三种提取器 + 一步引用：
> 1. **JSON Extractor**（首选）：对 JSON 响应用 JSONPath 提取，如 `$.data.token` 填入提取器，Name of variable 设为 `token`；
> 2. **正则提取器**：通用文本，如 `"token":"(.*?)"`，取第一个捕获组；
> 3. **边界提取器（Boundary Extractor）**：指定左右边界取中间值，不写正则更稳。
>
> 通用流程：上游接口加**后置处理器**提取 → 存为 JMeter 变量 → 下游接口参数填 `${token}`。调试时加 **Debug Sampler** 查看变量实际值。
>
> **解析**：追问点："提取全部匹配值怎么办"——JSON Extractor 的 Match No 设 `-1` 取全部（生成 `token_1`、`token_2`…与 `token_matchNr`），配合 ForEach 控制器遍历；"token 有时效怎么处理"——每个线程setUp 登录一次（一次性登录 setup 线程组）或前置校验过期自动重登。

### Q12.（简答 ★★★）压测发现 TPS 上不去、响应时间长，你的调优排查思路？

> **参考答案**：
> 按"**压测机 → 网络 → 中间件 → 应用 → 数据库**"从外到内分层定位：
> 1. **排除施压侧**：压测机 CPU/带宽/GC 是否打满（自己先累趴，数据全是假的）；
> 2. **网络层**：带宽、连接数限制、DNS/TLS 握手开销；
> 3. **中间件**：Tomcat 线程池、数据库连接池（HikariCP）是否排队满载、Nginx worker 配置；
> 4. **应用层**：`jstack` 看线程是否大量 BLOCKED（锁竞争）、`jstat`/`arthas` 看 GC 频率（频繁 Full GC 是 RT 抖动常见根因）、慢方法日志；
> 5. **数据库**：慢查询日志（`slow_query_log`）、`EXPLAIN` 看索引、`show processlist` 看锁等待；
> 6. 产出：每个假设用数据证实/证伪，给出瓶颈层 + 优化建议（加索引/扩连接池/加缓存/异步化）。
>
> **解析**：答题框架比具体命令重要——**先分层定位，再谈优化**，切忌直接说"加缓存"。追问点："怎么区分应用慢还是数据库慢"——应用日志打印接口内各阶段耗时（埋点/APM 链路追踪），SQL 耗时一目了然。

### Q13.（简答 ★★）负载测试、压力测试、稳定性（浸泡）测试的区别？

> **参考答案**：
> 1. **负载测试（Load）**：按**预期峰值负载**逐步加压，验证系统在目标并发下的响应时间与成功率是否达标——"预期范围内表现如何"；
> 2. **压力测试（Stress）**：**超出预期负载**持续加压直到系统极限/崩溃，找出系统最大容量与崩溃表现——"极限在哪、崩得体面吗"（快速失败还是雪崩）；
> 3. **稳定性测试（浸泡 Soak/Endurance）**：以**中等负载长时间运行**（7×24 小时/72 小时），验证内存泄漏、连接泄漏、磁盘增长等**慢性问题**。
>
> 三者是递进关系：先负载验证达标 → 压力找出极限 → 浸泡验证长跑稳定。
>
> **解析**：追问点："突发流量测试（Spike）"——瞬间加载到峰值再回落，验证弹性扩容；"浸泡测试为什么要做"——很多泄漏问题单次请求看不出来，必须靠时间累积暴露。

### Q14.（简答 ★★★）完整描述一次性能测试的流程。

> **参考答案**：
> 1. **需求分析**：明确压测目标（接口范围、指标要求——如 5000 TPS 下 RT<200ms、成功率 99.9%），收集生产流量模型；
> 2. **方案设计**：确定压测场景（单接口基准/混合业务场景）、并发模型、加压策略（梯度/阶梯）、监控项；
> 3. **环境与数据准备**：独立压测环境（配置与生产等比例）、造数（账号/库存/基础数据）、监控部署（服务器/数据库/JVM）；
> 4. **脚本开发**：JMeter/LoadRunner 录制或编写脚本，参数化 + 关联 + 断言，先单用户调通；
> 5. **基准测试**：单用户/低并发跑基准，拿到基线数据；
> 6. **正式执行**：按场景梯度加压，每轮记录 TPS/RT/资源曲线，观察拐点；
> 7. **结果分析与调优**：定位瓶颈（应用/DB/配置）→ 优化 → 回归压测验证，直至达标；
> 8. **报告输出**：容量结论（最优 TPS、对应并发数）、瓶颈与优化记录、扩容建议、风险清单。
>
> **解析**：答题要点是"**目标驱动、基准先行、压测-调优闭环**"。追问点："为什么先跑基准"——没有基线就无法判断优化是正收益还是负收益。

### Q15.（简答 ★★）TPS 和 QPS 的区别是什么？如何换算？

> **参考答案**：
> - **QPS（Queries Per Second）**：每秒**查询/请求**数，通常指对一个接口的请求量；
> - **TPS（Transactions Per Second）**：每秒**事务**数，一个"事务"可以包含**多个请求**（如一次下单 = 登录 + 加购 + 下单 3 个请求）。
> - **换算关系**：单接口事务（1 事务 = 1 请求）时 TPS = QPS；1 事务含 n 个请求时 **QPS = TPS × n**。
>
> 实践口径：团队内部常混用，汇报时**先对齐口径**（按事务还是按请求统计），避免差一个数量级。
>
> **解析**：追问点："聚合报告里的 Throughput 是什么"——JMeter 按请求统计的吞吐量（每秒完成请求数），对应 QPS 口径；"日峰值流量怎么换算成 TPS 目标"——日请求量 × 峰值集中系数（如 20% 在 1 小时内）÷ 3600。

### Q16.（简答 ★★）接口响应时间由哪几部分构成？多快算"快"？

> **参考答案**：
> **RT = 网络传输时间 + 服务端处理时间（N 层串联）+ 浏览器/客户端渲染时间**。拆解一个 HTTP 请求：DNS 解析 → TCP 握手/TLS 握手 → 发送请求 → 服务端排队 + 处理（含调用下游/DB）→ 响应返回 → 客户端渲染。
> - **通用参考标准**（电商 Web 场景）：2/5/10 原则——2 秒内优秀，5 秒内可接受，超过 10 秒用户流失；
> - **核心接口更严**：登录/支付等核心操作一般要求 RT < 1s（P95 口径）；高并发系统内部服务按毫秒级规划；
> - **统计口径**：看 P95/P99 而非平均值——平均值掩盖长尾（1% 的超时请求往往是事故来源）。
>
> **解析**：追问点："平均值和 P99 为什么要一起看"——平均 50ms 但 P99 5s，说明有长尾请求（GC、锁、慢 SQL），需要按分位数做 SLA；"网络耗时怎么单独测"——抓包看 TCP/TLS 阶段耗时，或对比内网/外网同接口 RT 差值。

### Q17.（简答 ★★）JMeter 的集合点（同步定时器/Rendezvous）有什么作用？

> **参考答案**：
> **集合点让多个虚拟用户在同一时刻"集结"后同时发起请求**，用于模拟瞬时高并发场景（秒杀开抢、整点活动）：
> - 配置：Synchronizing Timer 设定**集合用户数**（Number of Simulated Users to Group by）与**超时时间**；
> - 行为：线程到达集合点后等待，凑够设定人数（或超时）后**同时释放**，形成请求尖峰；
> - 对比不加集合点：默认线程按 Ramp-up 均匀启动，请求是"平稳流"而非"尖刺"。
>
> **解析**：追问点："集合用户数设得比线程数大会怎样"——凑不满按超时放行；"什么时候不该用"——测稳态吞吐时不要用（真实用户不会同时对齐），集合点只用于尖峰场景验证。

### Q18.（简答 ★★）JMeter 中常用的断言有哪些？

> **参考答案**：
> 1. **响应断言（Response Assertion）**：最常用——校验响应文本/响应码/响应头是否包含、等于、匹配（支持正则）指定内容；
> 2. **JSON 断言（JSON Assertion）**：按 JSONPath 校验字段值，如 `$.code == 0`；
> 3. **JSON JMESPath Assertion**：JMESPath 语法的 JSON 断言（过滤/投影更强大）；
> 4. **持续时间断言（Duration Assertion）**：校验响应时间不超过阈值（如 500ms）；
> 5. **大小断言（Size Assertion）**：校验响应体大小范围；
> 6. **XPath/BeanShell/JSR223 断言**：复杂逻辑用脚本断言（如响应解密后校验）。
>
> 压测脚本必须带断言——**没有断言的压测不知道"成功"的是什么**（可能压的是报错接口）。
>
> **解析**：追问点："压测断言怎么平衡开销"——断言在压测机执行，简单断言（响应码+关键字）开销可忽略，避免全量复杂正则；"聚合报告 Error% 和断言的关系"——断言失败会计入 Error%。

### Q19.（简答 ★★★）单台 JMeter 压不动了怎么办？说说分布式压测的原理与配置要点。

> **参考答案**：
> **瓶颈判断**：压测机 CPU > 80%、带宽打满、GC 频繁——施压端先饱和，数据不可信，需要**分布式（Master-Slave）**：
> 1. **架构**：1 台 **Master（控制机）**下发脚本并汇总结果，N 台 **Slave（负载机/执行机）**实际发起请求；
> 2. **配置要点**：
>    - 所有机器同一 JMeter + JDK 版本，同一网段（RMI 通信）；
>    - Slave 启动 `jmeter-server`（监听 1099 等端口），Master 的 `jmeter.properties` 配 `remote_hosts=slaveIP1,slaveIP2`；
>    - 参数文件（CSV）**每台 Slave 都要放一份**，各自读本地路径；
> 3. **并发计算**：脚本线程组设 N 时，总并发 = N × Slave 台数；
> 4. 防火墙/安全组放行 RMI 端口，各机器时间同步。
>
> **解析**：追问点："结果怎么汇总"——Master 聚合所有 Slave 数据；"分布式要注意什么"——Slave 机器配置尽量一致、时间同步（否则 RT 统计错乱）、内网带宽充裕（万兆理想）。

### Q20.（简答 ★★★）压测时需要监控哪些服务器指标？怎么搭建监控体系？

> **参考答案**：
> **四层监控对象**：
> 1. **硬件/OS 层**：CPU 使用率与负载、内存与 swap、磁盘 IO（iostat）、网络带宽与连接数；
> 2. **应用层**：JVM 堆内存与 GC（次数/耗时）、线程池活跃数与队列、接口耗时分布、错误日志；
> 3. **中间件层**：数据库连接池使用率、慢查询、Redis 命中率、MQ 堆积；
> 4. **压测侧**：TPS、RT 分位数、成功率。
>
> **常用体系**：**Prometheus + node_exporter（采集）+ Grafana（看板）+ Alertmanager（告警）**；JVM 用 JConsole/Arthas；MySQL 用 `show processlist` + 慢查询日志；轻量场景用 **nmon** 采样后离线分析。
>
> **解析**：答题要点是"**施压端与被压端都要监控，先看资源曲线再下结论**"。追问点："CPU 高但 TPS 低说明什么"——可能锁竞争/频繁 GC/低效算法，结合线程 dump 定位；"监控本身的性能开销"——采集频率别过密，避免影响压测数据。

### Q21.（简答 ★★★）数据库连接池对性能有什么影响？连接数怎么设置？

> **参考答案**：
> **连接池的作用**：复用 TCP 连接，避免每次请求都经历"建连认证销毁"（MySQL 建连开销毫秒级，高并发下是灾难）。
> - **连接池过小**：请求排队等连接 → RT 上升、TPS 上不去（应用层瓶颈常见根因）；
> - **连接池过大**：数据库侧上下文切换、锁竞争加剧，反而整体下降；MySQL 单实例建议并发连接数与 `max_connections`、CPU 核数匹配（经验：CPU 核数 × 2 左右起步，压测验证）；
> - **关键参数**（HikariCP）：`maximumPoolSize`（最大连接）、`connectionTimeout`（获取连接超时）、`idleTimeout`。
>
> 现象对照：RT 曲线突然抬升且应用日志出现 `Connection is not available, request timed out`——优先查连接池。
>
> **解析**：追问点："连接池大小能拍脑袋吗"——不能，用压测梯度验证（连接数从 10/20/40 逐步加），看 TPS 与连接池等待指标的拐点；"连接泄漏怎么发现"——连接池监控活跃连接只增不减，最终耗尽报错。

### Q22.（简答 ★★★）缓存穿透、缓存击穿、缓存雪崩分别是什么？怎么应对？

> **参考答案**：
> 1. **穿透**：查询**根本不存在的数据**，缓存和 DB 都没有 → 每次都打到 DB（恶意请求放大）。应对：**布隆过滤器**拦截不存在的 key；不存在的结果也缓存短时间（空值缓存）；接口层参数校验；
> 2. **击穿**：某个**热点 key 过期瞬间**，大量并发同时打到 DB 重建缓存。应对：**互斥锁**（只放一个线程去查 DB 重建，其他等待）、热点 key **逻辑过期**不物理删除；
> 3. **雪崩**：**大批 key 同时过期**（或缓存实例宕机）→ 请求洪峰全部落 DB。应对：过期时间加**随机抖动**、缓存集群高可用（哨兵/集群）、多级缓存、限流降级兜底。
>
> 性能测试视角：压测时要专门设计这三类场景（不存在数据、热点过期、批量过期），验证系统容错。
>
> **解析**：记忆锚点——穿透"**查不存在的**"、击穿"**单个热点过期**"、雪崩"**大面积失效**"。追问点："缓存与 DB 双写不一致怎么测"——更新后立即读、延迟读、并发读写交叉验证一致性。

### Q23.（简答 ★★★）发现一条慢 SQL，你的定位与优化思路？

> **参考答案**：
> 1. **定位慢 SQL**：开启慢查询日志（`slow_query_log`，阈值 `long_query_time`），或从 APM/`show processlist` 抓到具体语句；
> 2. **执行计划分析**：`EXPLAIN` 看关键列——`type`（出现 ALL 全表扫描要警惕）、`key`（是否用上索引）、`rows`（扫描行数）、`Extra`（Using filesort / Using temporary 是坏信号）；
> 3. **常见优化手段**：
>    - 建索引：WHERE/ORDER BY/JOIN 字段，组合索引注意**最左前缀**；
>    - 改写 SQL：避免 `SELECT *`、避免索引列上使用函数/隐式转换、大事务拆小；
>    - 深分页优化：`LIMIT 100000,20` 改为游标方式（`WHERE id > 上次最大id LIMIT 20`）；
>    - 数据量大考虑读写分离、分库分表；
> 4. **验证**：优化后 `EXPLAIN` 复查 + 压测对比 RT。
>
> **解析**：追问点："索引为什么失效"——对索引列做运算/函数、`LIKE '%xx'` 前缀模糊、隐式类型转换（varchar 列传数字）、组合索引不满足最左前缀；"索引是不是越多越好"——不是，索引加速读但拖慢写、占空间。

### Q24.（简答 ★★★）什么是容量规划？如何估算系统需要多少台服务器？

> **参考答案**：
> **容量规划 = 用压测数据反推生产资源**，回答"多少台机器能扛住业务峰值"：
> 1. **定目标**：从业务推算——日订单量 × 峰值集中系数 → 峰值 QPS 目标（如大促预估流量是日常 5 倍）；
> 2. **测单机能力**：单台机器（固定配置）压测得到**单机最优 TPS**（找拐点，而不是极限 TPS——留 30% 余量）；
> 3. **估算**：所需机器数 = 峰值 TPS ÷ 单机最优 TPS × 冗余系数（1.5~2 倍，覆盖故障与扩容窗口）；
> 4. **验证**：按估算规模搭建集群再压一轮全链路，验证线性扩展比（加机器是否成比例提升——出现"加机器不涨 TPS"说明存在共享瓶颈，如 DB/锁/带宽）。
>
> 输出物：容量规划表（场景 × TPS 目标 × 机器数 × 成本），给扩容决策做依据。
>
> **解析**：追问点："为什么不能用极限 TPS 计算"——极限状态无余量，一次抖动就雪崩；"扩展性验证怎么做"——1 台 → 2 台 → 4 台分别压，看 TPS 是否近似翻倍（不到 1.8 倍说明存在共享瓶颈）。

### Q25.（简答 ★）什么是基准测试（Benchmark）？为什么压测前要先做基准？

> **参考答案**：
> **基准测试 = 单用户/低并发下测量系统的基线性能**（单接口 RT、单机吞吐）。
> - **作用**：① 拿到"无损状态"的基线数据，后续高并发测试的**对照参考**；② 提前暴露单请求级别的问题（脚本错误、环境不通、单次请求就慢）；③ 验证脚本正确性（断言全部通过）；
> - **做法**：1 个线程、循环 N 次，记录 RT 稳定值；必要时逐步 1→2→5→10 线程观察线性度。
>
> 没有基线就直接高压，出了问题分不清"本来就慢"还是"压出来的问题"。
>
> **解析**：追问点："基准数据和容量测试什么关系"——单机基准 × 机器数是容量规划的理论上限；"基准测试和冒烟测试的区别"——基准关注性能基线，冒烟关注功能可用性，两者都是正式压测的前置。

### Q26.（简答 ★★）一份性能测试报告应包含哪些内容？

> **参考答案**：
> 1. **测试概述**：目的、范围、时间、环境（配置清单——压测机与被测机规格）、版本号；
> 2. **指标结论**（核心）：各场景的 TPS、RT（平均值 + P95/P99）、成功率，与**目标指标对比**给出"达标/不达标"结论；
> 3. **曲线与数据**：TPS/RT 随并发变化的梯度图、服务器资源曲线（CPU/内存/IO/网络）；
> 4. **瓶颈分析与优化记录**：发现的问题（现象→定位过程→根因）、优化措施与优化前后对比数据；
> 5. **容量结论与建议**：系统最大容量、拐点并发数、扩容建议、遗留风险（未覆盖场景、待优化项）。
>
> **解析**：报告的受众是**项目组与领导**，核心是"**结论先行 + 数据支撑**"——第一页就是达标结论与容量数字，过程细节放附录。追问点："为什么要写遗留风险"——测试范围的诚实声明，也是上线评估的输入。

### Q27.（简答 ★★★）性能测试中如何发现与定位内存泄漏？

> **参考答案**：
> 1. **现象识别**：稳定性测试（浸泡）中**内存曲线只涨不跌**（Full GC 后堆占用基线持续抬升），最终频繁 Full GC → RT 抖动 → OOM；
> 2. **定位手段（Java）**：
>    - `jstat -gcutil <pid>` 观察 GC 后老年代占用是否回收；
>    - `jmap -histo` / **MAT 分析堆转储**（`jmap -dump`），找对象实例数与 Retained Size 异常的类；
>    - 常见根因：**静态集合无限累积**（Map 只加不删）、ThreadLocal 未 remove、监听器/连接未关闭、缓存无上限；
> 3. **测试设计**：长时间浸泡 + 每轮请求压同一批接口，对比"请求前 vs GC 后"的堆基线；
> 4. **对照验证**：修复后重复浸泡测试，曲线应呈锯齿状（涨后回落）。
>
> **解析**：追问点："内存泄漏和内存溢出的区别"——泄漏（该回收的没回收，缓慢累积）是因，溢出 OOM（内存不够用）是果；"压测时怎么快速判断有没有泄漏"——看 Full GC 后的老年代占用是否逐轮抬高。

### Q28.（简答 ★★★）秒杀/抢购场景的性能测试怎么设计？

> **参考答案**：
> 秒杀的特点是**瞬时尖峰 + 热点读 + 库存竞争**，测试设计围绕这三点：
> 1. **场景模型**：瞬时放压（集合点/阶梯秒级加压到峰值），远超日常容量 10~100 倍的短时洪峰；
> 2. **分层验证**：
>    - **前端/网关**：限流（令牌桶）是否生效、静态资源 CDN 卸载；
>    - **缓存层**：商品详情热点读的命中率、Redis 抗压；
>    - **核心写**：下单/扣库存——**超卖验证**（并发扣减后库存不为负，压测后 DB 校验 `库存 >= 0`）、防重复下单；
>    - **降级与熔断**：超出容量时系统是否优雅拒绝（排队页/售罄页）而不是雪崩；
> 3. **数据断言**：压测后核对"成功订单数 = 库存扣减数"，不超卖不少卖；
> 4. **观察恢复**：洪峰过后 TPS/RT 是否回落正常（验证弹性与资源释放）。
>
> **解析**：追问点："怎么模拟同一时刻抢同一商品"——JMeter 集合点 + 相同商品 id 参数；"库存扣减怎么测并发正确性"——压测后对账（订单数 vs 库存变化），SQL 层用乐观锁/分布式锁验证并发安全。

### Q29.（简答 ★★）压测需要大量测试数据，你的造数方案有哪些？

> **参考答案**：
> 1. **脚本批量插入**：Python + 数据库驱动 / 存储过程循环 insert（百万级数据最快，注意分批提交避免大事务）；
> 2. **JMeter 预热造数**：用压测脚本本身调用业务接口造数（更贴近真实数据分布，但慢）；
> 3. **生产数据脱敏复制**：从生产导出 + 脱敏（最真实，注意合规）；
> 4. **数据工厂/生成器**：Faker 库生成随机姓名手机号，保持数据多样性（覆盖不同长度/类型边界）；
> 5. **关键原则**：数据量级要**接近生产**（千万级表和百级表的执行计划完全不同）；CSV 参数文件提前分片；造数后重建索引/更新统计信息。
>
> **解析**：追问点："为什么数据量必须接近生产"——数据量决定执行计划（百万行走索引，百行全表扫可能更快），量不对性能结论失真；"压测数据互相污染怎么办"——每轮压测重置数据（truncate + 重新造数）或用标记隔离。

### Q30.（简答 ★★★）为什么正式压测推荐 CLI（no-GUI）模式？哪些因素会让压测结果失真？

> **参考答案**：
> **GUI 模式的开销**：监听器实时渲染图形占大量 CPU/内存，施压机资源被 JMeter 自身吃掉，TPS 数据偏低且抖动——**测的是 JMeter 而不是系统**。
> - **正确姿势**：CLI 运行 `jmeter -n -t plan.jmx -l result.jtl -e -o report/`（生成 HTML 报告），监听器只留必要的（或干脆移除）；
> - **其他失真因素**：
>   1. 压测机带宽不足（尤其下载类接口）；
>   2. 压测机与被测机同机部署（资源互抢）；
>   3. 断言缺失（压的实际是失败请求）；
>   4. Think time 配置与业务不符；
>   5. 走了代理/VPN、DNS 未预热；
>   6. 结果包含脚本预热阶段（首个请求含建连/冷缓存）——剔除预热数据再统计。
>
> **解析**：追问点："Windows 和 Linux 谁做施压机好"——Linux 资源开销低、可调文件句柄数（`ulimit -n`）与 TCP 参数，正式压测首选；"文件句柄不足什么现象"——大量 `Too many open files` 报错，压测中途失败率飙升。

### Q31.（简答 ★★）HTTP 长连接（keep-alive）对性能测试有什么影响？

> **参考答案**：
> - **建连开销**：短连接每次请求都要 TCP 三次握手（高 RTT 下还要 TLS 握手），长连接复用连接发多个请求——**RT 更低、TPS 更高**，这是生产默认行为；
> - **压测配置**：JMeter 的 HTTP 请求默认值中 `Use KeepAlive` 要与生产一致；JMeter 的 `httpclient4.time_to_live` 控制连接复用时长；
> - **常见失真场景**：压测脚本没开 keep-alive 而（或反之）生产配置不一致 → 压测数据与线上表现对不上；
> - **服务端视角**：连接池（如 Tomcat maxConnections）、TIME_WAIT 数量都受连接模式影响——短连接压测会产生大量 TIME_WAIT。
>
> **解析**：追问点："keep-alive 会不会占用太多服务端资源"——有 idle 超时回收（keep-alive timeout），压测时线程数与连接数要匹配；"怎么验证压测走了长连接"——抓包看请求是否复用同一 TCP 四元组。

### Q32.（简答 ★★★）常见的服务端性能优化手段有哪些？

> **参考答案**：
> 按"**接入层 → 应用层 → 缓存层 → 数据层 → 架构层**"罗列：
> 1. **接入层**：Nginx 负载均衡与动静分离、CDN 卸载静态资源、连接复用（HTTP/2）；
> 2. **应用层**：线程池参数调优、异步化（MQ 削峰，非核心逻辑异步）、批量接口合并调用、代码热点优化（减少循环内 DB 调用）；
> 3. **缓存层**：多级缓存（本地 Caffeine + Redis）、缓存预热、合理 TTL 防雪崩；
> 4. **数据库层**：索引优化、读写分离、分库分表、连接池调优、慢 SQL 治理；
> 5. **JVM 层**：堆大小与 GC 器选择（G1/ZGC）、避免频繁 Full GC；
> 6. **架构层**：服务水平扩容、热点数据单独部署、限流熔断保护核心链路。
>
> **纪律**：每次只改一个变量 → 压测回归对比 → 确认收益再叠加，避免"一堆优化上完不知道哪层起效"。
>
> **解析**：答题按层次展开比罗列散点专业。追问点："最优先的优化顺序"——先定位（监控/链路追踪）再优化，经验上性价比排序：索引/SQL > 缓存 > 异步 > 扩容。
